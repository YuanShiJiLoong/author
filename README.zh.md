# ✍️ Author — AI-Powered Creative Writing Platform

> AI 驱动的网文创作平台 | AI-Powered Web Novel Writing Studio

**Author** 是一款面向小说作者的 AI 辅助创作工具。它将专业的富文本编辑器、智能 AI 写作助手和完整的世界观管理系统整合在一起，为创作者提供一站式写作体验。

🌐 **在线体验**：[author-delta.vercel.app](https://author-delta.vercel.app)

📦 **Gitee 镜像（国内加速）**：[gitee.com/yuanshijilong/author](https://gitee.com/yuanshijilong/author)

## 💬 为什么做这个项目

我用 AI 已经很长时间了。从 ChatGPT 3.5 开始，几乎每一代主流模型我都拿来写过小说。

<details>
<summary><b>📝 我用过的模型（个人体会，2026 年 10 月）</b></summary>

以下是我自己写小说时的体会，并非严格测评。模型一直在更新，看法也会跟着变。

**ChatGPT 3.5 → GPT-4o**

最早用的是 ChatGPT 3.5。之后是 GPT-4o，我连续用了一两个月，它是第一个让我觉得"这就是人工智能"的模型。

**Gemini 2.0 Pro → 2.0 Thinking → DeepSeek R1**

Gemini 2.0 Pro 当时还没有推理，有 200 万 token（词元）的上下文，但到十万左右就开始忘东忘西。之后用过 2.0 Thinking，以及 2025 年初的 DeepSeek R1。

**Gemini 2.5 Pro：第一个把人物写活的模型**

2.5 Pro 出来之后，特别是 2025 年 3 月的 0325 版，那段时间我几乎每天都在用。它当时写作和其他方面都很强，上下文长，也是第一个能把角色反应写活、写出人物情感的模型。那段时间我没再用别家，只是测试过一些，比如 o3，主要用在科研上，它的科研能力比较强。

**人物被写成生物结构**

从 o3 之后，不少模型写人容易写成一堆生物结构，DeepSeek 也有这个问题，瞳孔缩了几毫米、心跳快了几下、脉搏多少都要写。到 Gemini 3.0，这个问题就很明显了，动不动就写肢体、脊椎。Claude Opus 4.6 刚发布时最严重，但过了十天半个月就改善了很多，不知道是不是做了后训练调整。

**Gemini 3.0 / 3.1：浮夸、极端**

Gemini 笔下的人物容易浮夸、极端，这一点在写作圈里几乎是公认的，到 Gemini 4 Argon 也还有一些。Gemini 在角色扮演用户里用得很多，免费层级的数据按协议也会用于改进模型。我个人猜测这对它的写作倾向有影响，当然也只是猜测。

**Claude Opus 4.6：唯一真正重视伏笔的模型**

改善之后，它的细节非常丰富，是个稳重、厚重的模型。在 Opus 5.5 出来之前，它的写作一直领先。

它是唯一一个能写出触动人心的句子的模型。写到几十万字，它会突然把前面一句我根本没强调过的话拉出来，跟后面的情节、人物的回应对上，人物就有了厚度。它也是第一个能提升我写作上限的模型。

它塑造人物，靠的是极其丰富的心理描写和意识流，再配上行为和对白。缺点是人物表面上很平静，反应都在心里。你对人物做出举动或者跟他说话，他可能只回一个字，言简意赅，内心活动却很丰富。有人说这是"死人感"，我不这么看。人最重要的是内心，心理丰厚了，人物才更有活人感，它缺的只是表面那一层。

Gemini 正好相反，它最注重表面，或者说只停留在表面。人物反应浮夸、极端，让人觉得很有活人感。在我看来，这样的人物描写太肤浅。不过写狭义的爽文，靠表面的浮夸撑起爽感，它还是很有用的。

2026 年 8 月起，Opus 4.6 开始变化，9 月以后尤其明显。人物的回应没那么冷淡了，但意识流的写法明显少了，人物厚度不如从前。现在我主要用它写伏笔，日常已经不如 Opus 5.5 顺手。

**Opus 4.7 → 4.8 → 5：一路下滑**

4.6 之后几代明显变差。Opus 5 满篇自造的缩写和行话，别说写小说，搞编程的人也看不懂它在写什么。

**Opus 5.5：第二个提升我上限的模型**

一开始我不太看好它。它的语言很舒服，看得出在语言上下了功夫，但扩写能力不够。真正拿它参与创作之后，发现它很有东西。它比 4.6 少了很多意识流，人物反应好了一些，但有时会连着几个"嗯"这种单字回复，分寸还没完全拿准。它也不如 4.6 重视伏笔。

现在我更习惯用 5.5。4.6 和 5.5 是互补的，如果再加上 Gemini 那种跳脱的反应，三者中和一下，就算真正跨代了。

**GPT-5 到 GPT-6 Ultra：会说人话了，但爱推进、爱说教**

GPT-5 到 5.4 基本不说人话。5.5 好一些，5.6 比较好，5.6 和 GPT-6 Ultra 的 AI 味也少了很多，但还在。

GPT 的老毛病有两个：

- **一味推进剧情。** 不懂伏笔，不懂铺垫，好像第一章就想把结局写完。
- **借角色说教。** 它的说教不会直接说出来，它会悄悄改角色。一个杀人放火、毫无底线的黑帮老大，到它手里突然变得很有底线，借角色的嘴告诉作者"这样不道德"。写小说难免有黑暗情节，这很影响创作。Opus 5.5 也有一点，但没 GPT 严重。

**Gemini 4 Argon：会写爽文，节省时间**

它擅长东亚网文那种狭义的爽文，知道情节该怎么走，世界知识也很强。外貌描写是立绘式的，简洁有力、形象鲜明，不用提示就会自己写；Claude 不提醒就不会这样写。它也爱推进剧情。

广义的爽文，比如伏笔回收带来的感动、人物写得很深刻，就不是它的强项。它能帮你省时间，但不能提升你的上限。想写有厚度的人物，还是要用 Opus 4.6 和 5.5。

**开源模型：能用了，但节奏还差一些**

我一直在测开源模型，节奏上都还差一些。DeepSeek V4.1 终于能用了，但输出很短（官方说对输出做了优化、缩短了长度），聊几轮之后稳定在三百字左右，写小说这样太累了；用词偏口语，但能把事讲清楚。Kimi K3 口碑很好，但写小说时文笔很口语化，偶尔还冒出打油诗式的句子。

<details>
<summary><b>💡 AI 味、提示词和测试</b></summary>

**什么是 AI 味**

很多人强调 AI 味，说不要用"不是……而是"。AI 味指的是把正确的用法放在了错误的地方，比如"不是……而是"、省略号、破折号，还有"指节泛白"这类搭配。这些都是人类正常使用的表达，用错了地方才成了 AI 味。写作和代码不一样，改一个停顿、删几个字、换一下语序，意思就完全不同。

AI 味也不是衡量写作水平的标准。现在的 AI 并非 AGI，有 AI 味很正常，自己改一改就行。如果一个模型写的东西改起来还不如自己重写，那就换一个用着更顺手、真正能节省时间或提升上限的模型。

**提示词不用买**

网上有很多人卖提示词，每一代模型出来都有人去买，没有必要。提示词的底层逻辑是一样的，本质上是一套核心框架。只要你能把想让模型做到什么讲清楚，就可以让模型帮你写。

我现在用的提示词，最早是 GPT-4o 帮我写的，后来用 Gemini 2.5 Pro 的深度研究（Deep Research）补充完善，之后一直在这个框架上迭代，每一代模型都适用。

**重点是上下文纠偏**

给模型塞一堆"要有人味""不要 AI 味""不要过度风格化"这类规则，效果有限。这些说法本身很主观，人和人之间都没有统一标准，模型每次的理解也不一样。

对 Opus 5.5 这种很懂人类语言的模型，更有用的是少样本示范和上下文纠偏：写作中发现它写偏了，当场纠正。它有了样本，就知道哪里不对、该往哪写，理解会越来越接近你的要求。老模型还是更依赖预设；在角色扮演等一些场景里，预设也仍然很重要。

**测试要自己做**

社交媒体上流行的测试，比如 3D 场景、鹈鹕骑自行车，拿来看模型有没有变差就够了，别拿来判断写作水平。每家的训练方向、数据比例都不一样。

维护一套你自己的测试，用你自己的内容去写，形成自己的判断。也别搞全自动测试，让模型自己跑完就只看结果；测试时你要自己参与、自己引导。我一开始主要测模型能不能把东西写长，扩写能力能反映它拓展情节的能力，这个方法对 Opus 4.6 很管用。到了 Opus 5.5 就不够用了，我改成让它真正参与实际创作，再系统地比较。

</details>

### 什么样的写作算好

- **人物要靠行为和内心立起来。** 性格和情感，要从他做了什么、说了什么、心里想了什么里透出来。给人下一个定义，或者只写生理反应，写不出真正的人。
- **伏笔要接得住。** 写到几十万字，把前面一句不起眼的话拉回来，和眼前的情节呼应上，人物就有了厚度。
- **好模型能抬高作者的上限。** 它写出的一句话，能让你想到更好的写法。

### Author 的方向

目前这个项目的重点在辅助写作。现在的模型能力还不足以自动创作，所以人类主导、模型辅助，是我做 Author 的一个重要方向。当然，这会随着模型能力的提高而做出取舍和改变。

### 为什么写作这么重要

写作是衡量模型通用性的一个重要模块。每个故事都是一个不同的世界，每个世界都有自己的物理规则。写作同时考验模型对世界的认识、对时空关系和人物情感的理解，也考验注意力、召回和长文记忆。

通用人工智能，重点就在"通用"两个字。

我并非专业作家，只写过几部网文，算是有资格参与评价。我本身是理工科专业，有一定的跨学科能力，所以这些看法应该有一定参考价值。以上都是个人见解。

> 希望所有使用这个项目的人，都能写出有人情味的作品，保住我们语言的火种。作家之外，也希望各行各业的人都尽自己的一份力。🔥

## ✨ 核心功能

### 📝 专业编辑器
- 基于 **Tiptap** 的富文本编辑器，支持加粗、斜体、标题、列表、代码块等
- **Word 风格分页**排版，所见即所得
- **正文备注 / 批注** — 选中句子即可添加纸页侧注，DOCX 批注版会导出为 Word 原生批注
- **KaTeX** 数学公式支持
- 字体、字号、行距、颜色自定义
- **桌面端与 Android 文字朗读** — 可朗读选中文字或当前章节，支持暂停、继续、音色和语速调节
- **当前段落高亮** — 可选的专注底色，并在编辑器失焦后保留细光标位置
- 实时字数/字符/段落统计

### 🤖 AI 写作助手
- **多 AI 供应商**：智谱 GLM / DeepSeek / OpenAI / Google Gemini / Claude / SiliconFlow / 火山引擎 / 阿里云百炼 / MiniMax / Moonshot + 自定义端点
- **智能模型拉取** — 一键从 API 拉取完整模型列表；供应商不再返回的已保存模型仍可管理和清理
- **续写 / 改写 / 润色 / 扩写**，一键生成
- **沉浸式写作引擎（Ghost Text）** 流式预览 — 像 Cursor 一样实时显示 AI 生成内容，支持接受/拒绝
- **自由对话模式** — 与 AI 讨论剧情、角色、设定
- **AI 对话发送快捷键** — 可选择 Enter 发送，或 Ctrl/⌘ + Enter 发送，同时作用于小输入框和全屏输入面板
- **AI 全局记忆（Context Engine）** — AI 自动感知你的角色设定、世界观、前文，保持剧情连贯
- **按卷选择 AI 参考** — 章节按卷分组，支持整卷或逐章勾选；取消全部参考后会保留空选状态
- **可选忽略删除线文字** — 默认关闭；开启后 AI 会跳过删除线文字，原始正文与格式保留
- **API 格式切换** — 阿里云百炼和 MiniMax 同时支持 OpenAI 和 Anthropic 两种 API 格式

### 📚 设定集管理
- **树形结构**管理角色、地点、物品、大纲、写作规则
- 三种写作模式：**网文** / **传统文学** / **剧本**，每种模式有专属字段
- 分类配色 + glassmorphism 视觉风格
- 可在完整设定集面板或左侧分类弹窗编辑模式中，为每个作品单独重命名顶层分类
- 设定内容自动注入 AI 上下文

### 💾 数据管理
- **本地优先** — 创作数据默认保存在浏览器 IndexedDB；仅在你主动开启云同步、WebDAV 或局域网传输时发送所选数据
- **快照系统** — 手动/自动版本存档，支持一键回滚
- **项目导入导出** — 完整项目 JSON 备份
- **多格式导出** — 导航栏一键导出本章或批量导出（TXT / Markdown / DOCX / EPUB / PDF），可选择正文版或批注版

### 📱 移动端
- **Android 应用** — 基于 Flutter 的原生应用，支持本地优先写作和更丰富的阅读模式设置
- 随时随地在手机上阅读和编辑你的小说
- Author Cloud 账号登录仅在官方网页版提供；移动端不提供账号登录

### 🌐 国际化
- 🇨🇳 简体中文 / 🇺🇸 English / 🇷🇺 Русский

### 🎨 界面体验
- 护眼暖色调 / 深色模式切换
- 新手引导教程
- 帮助面板 + 快捷键说明

## 🚀 快速开始

> 💡 **强烈建议**：对于只需满足日常写作需求的大多数用户，请[直接下载安装客户端](https://github.com/YuanShiJiLoong/author/releases/latest)使用。源码或 Vercel 部署适合需要进行**二次开发**，或希望配置 WebDAV、自己的 Author 同步服务器的高级用户。

### 环境要求
- **Node.js** 18+
- **npm** 9+ 或 **pnpm** 8+

### 安装

```bash
# 克隆仓库
git clone https://github.com/YuanShiJiLoong/author.git
# 国内用户推荐使用 Gitee 镜像（更快）
# git clone https://gitee.com/yuanshijilong/author.git
cd author

# 安装依赖
npm install
# 或使用 pnpm（无幽灵依赖问题）
# pnpm install
# pnpm approve-builds    # pnpm 需要手动激活原生构建包

# 配置环境变量（可选）
cp .env.example .env.local
# 编辑 .env.local 填入你的 API Key
# 也可以在应用内「设置」面板中配置
```

### 启动开发服务器

```bash
npm run dev
```

打开 [http://localhost:3000](http://localhost:3000) 即可使用。

### 生产构建

```bash
npm run build
npm start
```

### 子路径部署

仅当你的自部署应用挂载在域名子路径时设置 `NEXT_PUBLIC_BASE_PATH`。例如：

```env
NEXT_PUBLIC_BASE_PATH=/app
```

真实域名、备案信息、服务地址、凭据和运维配置应只保存在你自己的部署环境中，不要提交到本仓库。

### 部署到 Vercel

> 💡 **⚠️ 注意：** Vercel 部署不包含 Author 官方账号云服务，可使用本地存储、WebDAV/局域网或自己的 Author 同步服务器。

[![Deploy with Vercel](https://vercel.com/button)](https://vercel.com/new/clone?repository-url=https://github.com/YuanShiJiLoong/author)

### ☁️ 同步方式

- 基于账号的 Author Cloud 云同步仅在[官方网页版](https://free.author2.com/app)提供。
- 桌面端不连接 Author 官方云服务，可在 **偏好设置 → 云同步** 中使用 WebDAV、临时局域网传输或用户自己的 Author 同步服务器。
- 移动端不提供 Author Cloud 账号登录，可通过本地备份和导出转移数据。
- 源码和 Vercel 部署不包含官方账号服务，可使用 WebDAV/局域网或连接自己的 Author 同步服务器。

## 🧠 向量化 (Embedding) 与 RAG 设定检索

> 💡 此功能适用于设定集条目较多（>20 个）的长篇巨著。普通短篇创作通常不需要配置。

### 什么是向量化？

传统方式下，AI 对话时会将设定集的**所有条目**注入上下文。当条目数量庞大时，会超出模型的上下文长度限制。

**向量化检索（RAG）** 的做法是：将每个设定条目转化为一个数学向量，对话时 AI 自动计算语义相似度，只取出**最相关的几条设定**注入上下文，而不是全量塞入。

### 何时需要？

| 场景 | 建议 |
|------|------|
| 设定条目 < 20 个 | 无需开启，全量注入即可 |
| 设定条目 20~100 个 | 建议开启，提升召回精度 |
| 设定条目 > 100 个 | 强烈建议开启，重要设定不再被遗忘 |

### 如何配置

1. 打开**设定集** → **API 配置**
2. 找到「独立向量 API」开关并启用
3. 填写以下信息：

| 配置项 | 说明 |
|--------|------|
| **Embedding API Key** | 向量化模型的 API 密钥（可与对话模型共用同一供应商的 Key） |
| **Embedding Base URL** | 接口地址（如 `https://api.openai.com/v1`） |
| **Embedding Model** | 模型名称（见下方推荐） |

如果嵌入服务不要求 API Key，关闭复用聊天 Key 后，将嵌入 Key 留空即可。

#### 推荐模型

| 供应商 | 模型名称 | 特点 |
|--------|---------|------|
| OpenAI | `text-embedding-3-small` | 性价比高，1536 维 |
| OpenAI | `text-embedding-3-large` | 精度更高，3072 维 |
| 智谱 AI | `embedding-3` | 中文优化，2048 维 |
| SiliconFlow | `BAAI/bge-m3` | 多语言，免费额度 |

### 自动向量化机制

- **自动触发**：设定集条目发生变化后，系统自动防抖 3 秒再触发向量化，不干扰写作心流。
- **增量更新**：只对修改过的条目进行更新重建，不会全量重建，极致节省 API 额度与时间。
- **本地存储**：向量数据储存在本地浏览器 IndexedDB 中，不会上传到任何非你配置的服务器，保护知识产权。
- **自动初始化**：在导入设定集或多端同步拉取数据时，如果发现本地缺少向量索引，系统会自动后台构建。

### 手动重建向量

如果切换了 Embedding 模型、或向量索引出现异常，可以手动重建：

1. 打开**设定集** → **API 配置**
2. 点击「**重建向量索引**」按钮
3. 等待所有条目重新向量化完成

### 工作流程

```
用户编辑设定条目 → 自动防抖 3 秒 → 调用 Embedding API 获取向量
                                          ↓
                                   存储到本地 IndexedDB
                                          ↓
AI 对话时 → 将用户输入向量化 → 余弦相似度匹配 → 取 Top-K 相关设定注入上下文
```

## 💾 设定集导入格式说明

Author 支持从多种格式导入设定集：**JSON / Markdown / TXT / DOCX / PDF**。

### 核心结构：四个层级

导入系统使用**结构性标记**来严格区分以下四个层级。无论使用哪种格式，都必须遵循此套娃结构：
`分类（Category）→ 条目（Entry）→ 字段（Field）→ 值（Value，可多行）`

因此，**任意自定义分类、自定义标签、自定义字段都能被正确识别**并无损还原。

### 格式可靠性与层级标记对照表

| 等级 | 格式 | 分类 | 条目 | 字段 | 续行 |
|------|------|---------|---------|---------|---------|
| ⭐⭐⭐⭐⭐ (无损) | **JSON** | `category` | `name` | `content` 键值对 | `\n` 换行符 |
| ⭐⭐⭐⭐⭐ (无损) | **MD** | `## 分类名` | `### 条目名` | `**标签**：值` | 缩进内容 |
| ⭐⭐⭐⭐ (无损) | **TXT** | `│ 分类名` | `【条目名】` | `〈标签〉：值` | 缩进内容 |
| ⭐⭐⭐ (高保真) | **DOCX** | Heading 1 | Heading 2 | **加粗**标签+冒号 | 缩进段落 |
| ⭐⭐ (高保真) | **PDF** | `■ 分类名` | `◆ 条目名` | `▸ 标签：值` | 缩进内容 |

### 💡 兼容性设计与注意事项

1. **自动标签回退 (向后兼容)** — TXT/Markdown 中如果遇到无专用结构符（如只有 `姓名：张三` 而不是 `**姓名**：张三`），只要 `姓名` 属于已知的核心字段集，系统仍会自动兼容解析该字段。但想要 100% 确保触发并提取自定义字段，请务必加上结构符号。
2. **多行值处理** — 每当你使用了 `**标签**：` 或 `〈标签〉：` 起头后，所有接下来**带有 2 格缩进的行**都会被被视为该字段的正文（多行值提取），直到遇到下一个结构性标签为止。
3. **DOCX / PDF 解析限制** — PDF 使用专门设计的 `▸` 标识符提取，如果导入并非本系统生成的 PDF / DOCX 文件，系统会触发启发式解析尝试尽可能提取内容，但保真度无法达到 100%。
4. **JSON 最完整** — JSON 毫无疑问是最严谨、能够 100% 迁移所有属性（包括写入模式、作品配置信息）的格式。如果仅仅是为了更换创作设备，强烈建议首选 JSON 导入导出。

## 🔒 隐私与数据安全

### 本地存储（安全）
- 章节内容、设定集、快照等创作数据默认保存在浏览器 IndexedDB。主动开启 Author Cloud、WebDAV 或局域网传输后，所选同步数据会发送到你配置的服务或设备。
- 浏览器部署将 AI API Key 保存在 localStorage；桌面客户端使用操作系统安全存储加密保护。

### ⚠️ AI 功能的数据流向

当 AI 供应商支持浏览器访问，且未配置代理或联网搜索时，官方网页版会把你的 **API Key** 和**发送给 AI 的文字内容**从浏览器直接发送给供应商。

供应商不支持浏览器直连、配置了代理地址、启用联网搜索，或部署者关闭直连时，请求会先经过该部署的 API 接口再发送给供应商。桌面客户端会经过同一台电脑上的本地回环服务。

- 只在你信任的部署中填写 API Key。
- 如果供应商支持，优先使用权限受限、可随时撤销的 Key。
- 如需完全控制转发环境，可自行部署应用。
